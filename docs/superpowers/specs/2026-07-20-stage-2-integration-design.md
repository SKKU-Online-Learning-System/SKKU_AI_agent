# 2단계 기능 통합 및 실행 문서화 설계

## 목표

인증, 역할 기반 접근 제어, 과목 관리, 교수자 자료 업로드, 학생 과목 조회를
실제 API와 웹 화면에서 하나의 2단계 흐름으로 연결한다. 다른 개발자가
`README.md`만 읽고 PostgreSQL 실행, 마이그레이션, Seed, 서버 실행, 자동 테스트,
역할별 수동 검증을 재현할 수 있어야 한다.

이번 작업은 2단계 데이터 모델과 서비스 경계를 완성하는 데 집중한다. 문서 파싱,
청크 분할, 임베딩, RAG 검색, 챗봇 답변과 출처, 로그 및 통계 대시보드는 3단계
구현 범위로 남긴다.

## 현재 상태와 해결할 격차

현재 저장소에는 다음 기반이 있다.

- 세 역할의 Seed 계정과 예시 과목 두 개
- Argon2 비밀번호 검증과 JWT 로그인 및 현재 사용자 조회
- 백엔드 RBAC 서비스와 역할별 프론트엔드 보호 레이아웃
- 관리자 과목 목록, 생성, 수정, 활성화, 비활성화 API 및 웹 화면
- 역할별 접근 가능한 과목을 필터링하는 API
- `CourseMaterial` SQLAlchemy 모델과 Alembic 테이블

반면 자료 업로드 API는 임시 응답만 반환하며 파일과 DB 행을 저장하지 않는다.
자료 목록은 항상 비어 있고 삭제 API가 없다. 교수자 과목 및 자료 화면과 학생
과목 화면도 실제 API가 아닌 안내용 플레이스홀더다. 이번 작업은 이 격차를
테스트 우선으로 해소한다.

## 선택한 접근

SQLite 인메모리 데이터베이스와 임시 업로드 디렉터리를 사용하는 FastAPI 통합
테스트를 자동 검증의 중심으로 삼는다. 이 테스트는 빠르고 독립적이며 인증,
권한, CRUD, 파일 저장과 메타데이터 저장을 하나의 흐름으로 검증할 수 있다.

프론트엔드는 기존 Vitest 구성을 사용해 API 클라이언트와 주요 렌더링/상호작용을
검증한다. PostgreSQL, Alembic, 실제 두 서버를 함께 사용하는 검증은 README의
명령과 역할별 수동 체크리스트로 제공한다. 현재 저장소에 없는 Playwright 기반
브라우저 E2E 인프라는 이번 단계에 추가하지 않는다.

## 백엔드 구조

### 설정

백엔드 설정에 다음 값을 추가한다.

- `UPLOAD_DIR`: 업로드 파일 저장 루트, 기본값 `uploads`
- `MAX_UPLOAD_SIZE_BYTES`: 파일당 최대 크기, 기본값 `20971520`(20MB)

허용 확장자는 `.pdf`, `.pptx`, `.docx`, `.txt`로 고정한다. 설정과 README는 동일한
기본값을 사용한다.

### 자료 저장 서비스

파일 검증과 저장 책임은 자료 라우트에서 분리한 서비스에 둔다. 서비스는 다음을
담당한다.

1. 원본 파일명에서 확장자를 추출하고 허용 목록을 검사한다.
2. 업로드 스트림을 제한된 크기의 청크로 읽는다.
3. 첫 바이트가 없으면 빈 파일로 거절한다.
4. 누적 크기가 `MAX_UPLOAD_SIZE_BYTES`를 초과하면 즉시 거절한다.
5. UUID와 원본 확장자로 내부 파일명을 만들고
   `<UPLOAD_DIR>/<course_id>/<uuid>.<ext>`에 저장한다.
6. 실제 파일 크기를 계산한다.

파일 시스템 경로에는 사용자 제공 디렉터리 조각을 사용하지 않는다. 원본 파일명은
표시용 메타데이터로만 저장한다.

### 자료 API

API 계약은 다음과 같다.

- `GET /api/courses/{course_id}/materials`
  - 과목 접근 권한 필요
  - 생성 시각 내림차순으로 자료 반환
- `POST /api/courses/{course_id}/materials`
  - 과목 관리 권한 필요
  - `multipart/form-data`의 `file` 수신
  - 파일 저장과 `CourseMaterial` 생성 후 HTTP 201 반환
- `DELETE /api/courses/{course_id}/materials/{material_id}`
  - 과목 관리 권한 필요
  - 해당 과목 자료만 삭제 가능
  - DB 행 삭제와 저장 파일 제거 후 HTTP 204 반환

교수자는 본인이 담당하는 과목만 관리할 수 있고 관리자는 모든 과목을 관리할 수
있다. 학생은 접근 가능한 활성 과목의 자료 목록만 볼 수 있으며 업로드와 삭제는
403으로 차단된다.

응답은 실제 `CourseMaterial` 모델을 반영한다.

- `id`
- `courseId`
- `uploadedBy`
- `originalFileName`
- `fileType`
- `fileSize`
- `processingStatus`
- `processingError`
- `createdAt`
- `updatedAt`

내부 파일명과 절대 저장 경로는 API에 노출하지 않는다. 새 자료의
`processingStatus`는 항상 `pending`이다.

### 일관성과 오류 처리

- 잘못된 확장자, 빈 파일, 최대 크기 초과는 구체적인 메시지와 HTTP 422를 반환한다.
- 존재하지 않는 자료는 404를 반환한다.
- 다른 과목의 자료 ID를 사용해 삭제를 시도해도 404를 반환해 자료 존재 여부를
  누출하지 않는다.
- 파일 저장 뒤 DB 커밋이 실패하면 저장된 파일을 제거한다.
- 삭제할 파일이 이미 없어도 DB 행 삭제는 완료할 수 있게 하여 상태를 복구한다.
- DB 삭제가 실패하면 파일을 먼저 지우지 않는다. DB 커밋 후 파일을 제거한다.

## 프론트엔드 구조

기존 인증 공급자와 `apiRequest`를 재사용한다. 공통 API 모듈에 다음 타입과 함수를
추가한다.

- `CourseSummary`
- `CourseMaterial`
- `listCourses()`
- `listCourseMaterials(courseId)`
- `uploadCourseMaterial(courseId, file)`
- `deleteCourseMaterial(courseId, materialId)`

### 교수자 담당 과목

`/professor/courses`는 로그인한 교수자의 `GET /api/courses` 결과를 표로 표시한다.
담당 과목이 없을 때의 빈 상태, 로딩 상태, API 오류를 구분한다.

### 교수자 자료 관리

`/professor/materials`는 담당 과목 선택, 파일 입력, 업로드, 자료 목록,
`pending` 상태, 삭제를 제공한다. 허용 형식과 20MB 제한을 폼 가까이에 안내한다.
클라이언트 검증은 빠른 피드백을 위한 것이며 백엔드 검증을 대체하지 않는다.

### 학생 내 과목

`/student/courses`는 `GET /api/courses` 결과를 표시한다. 백엔드가 CourseAccess와
활성 상태를 기준으로 필터링하므로 비활성 과목과 권한 없는 과목은 목록에 나타나지
않는다. URL 직접 접근의 최종 권한 판정도 항상 백엔드가 수행한다.

### 역할별 경로 보호

기존 `ProtectedRoute`를 유지한다.

- 미로그인 사용자는 `/login?next=<현재 경로>`로 이동
- 학생 또는 교수자가 `/admin`에 접근하면 `/forbidden`으로 이동
- 각 역할 레이아웃은 자신의 역할만 허용

## Seed와 통합 흐름

Seed는 다음 데이터를 반복 실행 가능하게 유지한다.

- `admin@skku.edu`
- `professor@skku.edu`
- `student@skku.edu`
- 공통 비밀번호 `password123`
- `2026-2` 학기의 `인공지능개론`, `소프트웨어공학`
- 두 과목의 담당 교수자 관계
- 학생의 두 과목 접근 관계

자동 통합 테스트는 동일한 역할 관계를 격리된 DB에 구성하고 다음 흐름을 검증한다.

1. 세 역할 로그인과 JWT 발급
2. 관리자 과목 목록, 생성, 수정, 비활성화, 활성화
3. 교수자 담당 과목 조회, 자료 업로드, 목록, 삭제
4. 다른 교수자 과목 접근 403
5. 학생 접근 가능 활성 과목 조회와 비활성 과목 제외
6. 학생의 권한 없는 과목 직접 조회 403
7. 학생 및 교수자의 관리자 API 접근 403
8. 잘못된 JWT의 401

## 자동 테스트 전략

우선순위에 따라 테스트를 다음과 같이 구성한다.

### 1. 권한

- 관리자 API의 미인증 401과 비관리자 403
- 교수자의 다른 교수자 과목 조회/자료 관리 403
- 학생의 미수강 과목 및 비활성 과목 조회 403
- 학생의 자료 업로드/삭제 403

### 2. 인증

- Seed와 같은 세 역할 로그인
- `/api/auth/me`
- 잘못된 서명, 만료, 잘못된 타입, 존재하지 않는 사용자 JWT의 401

### 3. 과목 CRUD

- 관리자 목록, 생성, 수정, 비활성화, 활성화
- 교수자 목록에 담당 과목만 포함
- 학생 목록에 접근 가능한 활성 과목만 포함

### 4. 파일 업로드

- 허용 파일 저장과 DB 행 생성
- 내부 UUID 파일명
- `processing_status=pending`
- 목록 조회
- 삭제 시 DB 행과 파일 제거
- 잘못된 확장자, 빈 파일, 20MB 초과 실패
- 실패한 업로드가 파일 또는 DB 행을 남기지 않음

프론트엔드 테스트는 역할 보호 회귀, 공통 API 요청 형식, 교수자 자료 화면의
업로드/삭제 상태, 학생/교수자 과목 목록의 로딩·성공·빈 상태를 검증한다.

## 3단계 연결 지점

3단계 문서 처리기는 `pending` 자료를 조회해 `processing`으로 전환한 뒤 파싱,
청크 분할, 임베딩 저장을 수행한다. 성공 시 `completed`, 실패 시 `failed`와
`processing_error`를 기록한다.

업로드 API는 문서 내용을 해석하지 않으며 저장과 메타데이터 생성까지만 책임진다.
이 경계 덕분에 향후 동기 작업, 백그라운드 워커, 메시지 큐 중 하나를 선택해도
현재 API와 권한 규칙을 유지할 수 있다.

## 완료 조건

- 세 Seed 계정이 로그인 가능하다.
- JWT 인증과 역할별 웹/API 접근 제한이 검증된다.
- 관리자가 과목을 생성, 수정, 비활성화, 활성화할 수 있다.
- 교수자가 담당 과목과 자료를 실제 API로 관리할 수 있다.
- 학생이 접근 가능한 활성 과목만 실제 API로 조회한다.
- 업로드 파일과 `CourseMaterial` 메타데이터가 저장된다.
- 새 자료의 `processing_status`가 `pending`이다.
- 자동 테스트와 README 수동 체크리스트가 요구 시나리오를 포함한다.
- README만으로 로컬 2단계 환경을 실행하고 검증할 수 있다.
