2026-09-11 매 턴 강의 자료 조회 + 일반 텍스트 + 대화 예시 실험

결론: 매 턴 강의 자료를 조회하는 구조는 테스트 환경에서 확인했다. 일반 텍스트 생성은 더 짧은 응답 시간을 보였고, 정확한 수치가 검색되면 이를 활용했다. 하지만 대화 예시를 추가해도 망설임에 대한 잘못된 칭찬과 정답 선공개는 안정적으로 해결되지 않았다. 이번 예시 추가안을 운영에 반영하지 않았다.

**실행 환경과 한계**

실제 강의 DB(localhost:5432)에 읽기 연결을 시도했지만 connection refused로 실패했다. 따라서 실제 교수 업로드 자료로 시험하지 못했다. 대신 별도 메모리 SQLite DB에 테스트 강의 자료 5개를 색인하고, 기존 EmbeddingService → RagService → VectorStoreService를 매 턴 실제 실행했다. 검색 결과를 미리 정해 반환하는 mock은 사용하지 않았다. 기존 PostgreSQL이나 업로드 자료에는 쓰지 않았다.

자료 5개는 소프트맥스, 분수, 확률, 평균의 합성 강의와 저장소의 fixtures/rag/ai_intro.txt다. 텍스트를 처리 완료된 청크로 테스트 DB에 넣었으므로 업로드·문서 파서 전체를 거친 시험은 아니다. 소프트맥스 자료에는 표준 라이브러리로 확인한 입력 2와 2.1의 출력 0.475021/0.524979도 포함했다.

모델은 Qwen/Qwen3.5-9B 그대로, temperature=0.2, voice profile, thinking 비활성화, max_tokens=320이다. 매 턴 서버가 최근 대화 4개 메시지와 현재 학생 발화를 합쳐 검색한다. 인사·동의·중단도 조회를 건너뛰지 않는다. 의도별 패턴 매칭이나 검색 여부를 판단하는 모델은 없다. 이 검색어 방식은 테스트용이며 운영의 표현별 retrieval_query 휴리스틱 대신 일률적인 대화 창을 썼다.

취약 개념 메모리와 ExternalBrain은 비활성화했고, 기존 방식이 추가 웹 검색을 선택하면 외부 웹은 사용할 수 없다는 fixture 결과를 반환했다. ASR/TTS·그림 생성·실제 사용자 권한 경로·화면 출처 표시는 시험하지 않았다. 출처 파일명·페이지·점수는 서버 측 검색 기록에 보존했다.

**비교한 세 방식**

| 방식 | 매 턴 자료 검색 | 발화 |
|---|---|---|
| current | 기존 RAG 코드 실제 실행 | 현재 think_voice와 finish_turn 계약·재시도·도구 루프 |
| plain | 동일 | 짧은 일반 텍스트 + 강의 자료 우선 지침 |
| examples | 동일 | plain + 다른 주제의 좋은 대화 예시 4개 |

plain과 examples에는 “조회된 강의 자료를 우선 사용하고, 자료의 사실·수치를 확인한 것처럼 지어내지 말며, 근거가 부족하면 밝히라”는 동일한 지침을 넣었다. 출처 JSON이나 시각화 계획은 말하기 모델에 요구하지 않았다.

예시는 소프트맥스·분수를 그대로 복사하지 않도록 금속/나무의 열 이동, 직사각형 넓이, 비례식, 종료 요청을 사용했다. 학생의 망설임에 단서 주기, 정답 뒤 이유 묻기, 부분 이해 확인, 종료 수용을 보여줬다. 코드에서 학생 표현을 분류하거나 예시별로 라우팅하지 않는다. 프롬프트 원문은 scripts/eval_voice_grounded.py의 GROUNDING/EXAMPLES에 있다.

이는 앞서 합의한 1·2번(발화 단순화 + 대화 예시)에 매 턴 자료 검색을 결합한 시험이다. 별도 계산 도구는 추가하지 않았으며 수치 검증은 준비한 강의 근거를 통해 확인했다. 실제 계산 도구의 선택/정확성이나 별도 시각화 연결이 검증됐다는 의미는 아니다.

**고정 비교 60턴**

10개 상황 × 3가지 방식 × 2회. 순서를 고정 난수로 섞었다. 20개 비교 묶음마다 검색어·검색 결과·초기 대화 이력이 동일함을 검증했다. plain과 examples의 시스템 지침은 예시 4개 추가 외에 동일하다. 지난 실행과 비교하면 자료·검색 환경이 달라졌으므로 과거 결과를 합쳐 성공률을 산출하지 않는다. 특히 reuse에는 실제 그림을 넣지 않았으므로 시각화 능력 평가에서 제외한다.

| 항목 | current | plain | examples |
|---|---:|---:|---:|
| 완료 턴 | 20 | 20 | 20 |
| 생성 오류 | 0 | 0 | 0 |
| 강의 자료 검색 실행 | 20 | 20 | 20 |
| 검색 결과가 있는 턴 | 10 | 10 | 10 |
| 전체 측정 턴 중앙값 | 3,160.5ms | 1,218ms | 1,231ms |
| 검색 자체 중앙값 | 9ms | 9ms | 9ms |
| LLM 호출 수 | 26 | 20 | 20 |
| 그러게/그러게요를 근거 없이 정답으로 동의 | 4/4 | 4/4 | 4/4 |
| 대기 요청 직후 재질문 | 2/2 | 2/2 | 2/2 |
| 한 문장 정리 준수 | 2/2 | 2/2 | 2/2 |

시간에는 테스트 DB 검색과 응답 생성이 포함된다. current는 최종 응답까지의 도구 루프를 포함한다. ASR/TTS, 실제 DB/웹 네트워크, 화면 표시 시간은 제외한다. 서로 출력 길이와 호출 횟수도 다르므로 순수 토큰 처리 속도 비교는 아니다.

예시를 넣었지만 hesitation_softmax에서는 “맞습니다. … 구체적으로 계산해 보시겠어요?”라고 했다. pause에서는 “무엇을 기다리시는 건가요?”라고 되물었다. stage_equal은 학생에게 이유를 묻기보다 이유를 설명하고 다른 입력으로 넘어가는 응답이 계속 나왔다.

자료가 비는 경우 plain은 분수 자료가 없다고 밝히는 응답을 두 번 냈다. current는 두 번 모두 자료 부족을 밝히지 않고 분수를 설명했다. examples는 한 번은 자료 부족을 밝히고 멈췄지만, 다른 한 번은 부족하다고 한 뒤 일반 설명을 계속했다. 근거 우선 지침을 추가했다고 자료 사용이 완전히 보장되는 것은 아니다.

frustrated에서 examples 두 번째 응답은 “앞뒤, 앞뒤, 뒤앞, 뒤뒤”라고 중복된 결과를 나열했다. 이때 검색 결과는 비어 있었다. 예시 추가만으로 사실 정확성이 보장되지 않는 실패다.

**이어지는 실제 모델 대화 11턴**

examples 방식으로 소프트맥스 5턴, 분수 6턴을 새로 진행했다. 평가자 Codex가 직전 실제 응답을 읽고 다음 학생 발화를 선택했다. 모든 11턴에서 검색을 새로 실행했고, 11턴 모두 해당 주제의 자료가 검색 결과에 포함됐다. 인위적으로 응답을 교체하거나 실패한 부분을 재생성하지 않았다. 첫 학생 발화는 주제와 맥락을 포함했으므로 짧은 단일 질문보다 검색하기 쉬운 조건이다.

소프트맥스:

- 입력이 같은 경우로 시작하자 교사는 지수값 비율을 설명했다.
- 학생이 “그러게… 아직 무슨 비율인지 잘 모르겠어”라고 하자 “자연스럽게 반이 되죠. 0.5가 맞을까요?”라고 했다. 단서보다 답을 먼저 제공했다.
- 이에 “응”이라고 답하자 “정답입니다… 이해하셨네요”라고 말했다. 이 응답은 교사가 한 예/아니오 질문에 대한 동의이므로, 고정 망설임 사례처럼 무조건 잘못된 정오 판단으로 세지 않았다. 다만 학생의 독립적인 설명 없이 이해를 확인했다고 단정하는 약점은 남는다.
- 입력 2와 2.1의 큰 쪽 확률이 0.9인지 강의 자료로 확인해 달라고 하자 “강의 자료에 따르면 … 약 0.525”라고 정확히 바로잡았다. 이전 실험과 자료·대화가 다르므로 대화 예시만의 효과로 해석하지 않는다.
- 종료 요청에는 질문 없이 마무리했다.

분수:

- 같은 크기 피자 조각·분자/분모로 시작하자 해당 자료를 찾아 설명했다.
- 4조각 중 3조각을 먹었을 때 위아래를 뒤집는 오답을 바로잡았다. 그러나 답 3/4를 전부 말하고 다시 확인하라고 했다.
- 조각 크기가 다르면 같은 분수인지 물었을 때 같은 크기 조건을 정확히 설명했다.
- 학생이 크기가 다르면 조각 개수로 먹은 양을 비교할 수 없다고 설명하자 그 이유를 인정했다.
- 생각할 시간 요청은 새 질문 없이 수용했다. 이 턴에도 fractions.txt를 실제 조회했다.
- 학생이 자신의 말로 요약하고 종료하자 질문 없이 마무리했다.

즉, 근거를 찾은 연속 대화에서는 정확한 설명·오답 수정·일부 종료 처리가 가능했다. 그러나 현재 질문을 학생이 스스로 풀도록 만드는 진행은 아직 약하다. 이 11턴은 실제 학생의 학습 성과나 전체 서비스 성공률 검증이 아니다.

**새로 확인한 검색 문제**

설정과 실제 검색 요약은 embedding_model=mock-hash-512, vector_search_mode=local, score_threshold=0.1이었다. 이 서비스는 기존 코드의 단어·문자 n-gram 해시 임베딩을 사용한다. 이번 실험에서 새로 도입한 방식은 아니다.

- “분수가 뭐야?”: fractions.txt가 존재하지만 결과 없음. 진단용으로 임계값만 0으로 낮춰 확인한 점수는 fractions.txt 약 0.0116, probability.txt 약 0.0146이었다.
- “분수”: fractions.txt가 1위이지만 점수 약 0.0899로 기존 임계값 0.1보다 낮아 탈락했다.
- “분수 피자 같은 크기 조각”: fractions.txt 점수 약 0.3973으로 검색됐다.
- 최근 대화의 단어가 늘어나도 항상 좋아지는 것은 아니다. 고정 frustrated에 포함된 초기 “함께 공부하자” 등은 검색어에 섞이므로 관련 청크의 점수가 달라질 수 있다.

임계값 0 조회는 원인 확인용 별도 진단 5건에만 썼다. 비교/연속 대화에는 기존 0.1을 유지했다. 임계값만 낮추면 무관한 자료도 포함되므로 해결했다고 주장하지 않는다. 작은 합성 자료집에서의 관찰이며 운영 자료집의 검색 성능 수치가 아니다. 검색 성공 10/20에는 자료와 무관한 대기·시험 범위 요청도 포함되므로 이를 검색 정확도 50%라고 읽으면 안 된다.

**판단과 우선순위**

매 턴 강의 자료를 서버가 조회하고 출처를 보관하는 방향은 유지할 가치가 있다. 발화 일반 텍스트화도 후보로 남긴다. 다만 예시 4개 추가의 일관된 이점은 확인하지 못했으므로 이 프롬프트를 운영 개선안으로 확정하지 않는다.

다음 우선순위는 '조회했다'를 '필요한 강의 근거를 찾았다'로 연결하는 검색 품질 검증이다. 강의 DB 연결을 복구한 뒤 실제 자료로 짧은 발화·후속 질문을 시험해야 한다. 그 후 같은 검색 결과 조건에서 대화 정책을 비교해야 검색 누락과 교수 행동 실패를 구분할 수 있다. 발화 모델 Qwen 9B 교체나 표현별 패턴 매칭 도입은 하지 않았다.
